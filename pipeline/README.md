# פייפליין ניתוח טיפולים

קורא מסמכי PDF של טיפולי רכב, מחלץ מהם ביקורים, ומייצר את קובץ הנתונים
שהדשבורד טוען.

```bash
cd pipeline
pip install -r requirements.txt
python -m vehicle_maintenance.build          # -> ../public/vehicle-data.json
python -m pytest tests/ -q
```

## בנייה אוטומטית

ב-`main` הפייפליין רץ מעצמו על כל שינוי תחת `pipeline/`
(`.github/workflows/rebuild-vehicle-data.yml`), מריץ את הטסטים, בונה מחדש את
`public/vehicle-data.json` ודוחף אותו. אין צורך להריץ ידנית כדי שהדשבורד
יתעדכן — אבל כן כדאי, כדי לראות אזהרות לפני שדוחפים.

הטסטים רצים לפני הבנייה בכוונה: רשומה פגומה תפיל את הריצה בקול, במקום לייצר
דשבורד מלא במספרים שגויים.

## מסמכים סרוקים (OCR)

מסמך בלי שכבת טקסט לא ניתן לפרסור רגיל. במקום לתמלל ידנית:

```bash
pip install -r requirements-ocr.txt
export ANTHROPIC_API_KEY=...
python -m vehicle_maintenance.ocr data/fuel/paz_2026-07-24.pdf --kind fuel
python -m vehicle_maintenance.ocr <קובץ> --kind service --write
```

בלי `--write` זו הרצה יבשה: מודפסת הרשומה שתיווצר ותוצאות האימות.

**עיבוד באצווה.** אחרי העלאה של כמה מסמכים יחד, `--all` על תיקייה מעבד את כל
הסריקות שעדיין לא תומללו — מדלג על מסמכים עם שכבת טקסט (הם נקראים לבד) ועל
כאלה שכבר יש להם רשומה. כישלון אימות בקובץ אחד לא עוצר את השאר; בסוף מודפס
סיכום ורשימת הקבצים שדורשים טיפול ידני, וקוד היציאה שונה מאפס.

**למה מודל ראייה ולא OCR קלאסי.** בדקתי tesseract עם חבילת העברית על המסמכים
האמיתיים כאן. הוא זיהה את המבנה, אבל שיבש בדיוק את המספרים שחשובים: קרא
"35.00" במקום 335.00 בסה"כ החלפים, "20000" במקום 708.00 לתשלום, ואחרי הגדלת
התמונה הפך 42.532 ליטר ל-"22.2". מספר שגוי שנראה תקין הוא הכשל הגרוע ביותר
כאן, כי שום שלב אחריו לא יכול לזהות אותו.

**החילוץ הוא רק חצי מהעבודה.** כל קבלה נושאת את החשבון של עצמה — ליטרים × מחיר
= סה"כ, חלפים + עבודה + מע"מ = לתשלום — והמודול מתייחס לזהויות האלה כבדיקה על
הקריאה. מסמך שהמספרים בו לא מסתדרים מדווח לבדיקה ולא נכתב.

**זה לא חלק מהבנייה בכוונה.** הבנייה חייבת להישאר דטרמיניסטית, חינמית ובלי רשת;
השלב הזה עולה כסף, אינו דטרמיניסטי, ומייצר רשומה שנבדקת ונשמרת בגיט כמו כל
רשומה שנכתבה ביד.

## הוספת מסמכים

1. שמרו את ה-PDF ב-`data/pdfs/`.
2. הריצו `python -m vehicle_maintenance.build`.
3. אם המסמך הוא **סריקה** (תמונה ללא שכבת טקסט), הבנייה תדפיס אזהרה. במקרה כזה
   הוסיפו קובץ JSON ל-`data/manual/` עם תוכן החשבונית — ראו
   `data/manual/README.md` והדוגמאות שם. כך הביקור נספר בניתוח במקום ליפול בשקט.

## מבנה

| קובץ | תפקיד |
| --- | --- |
| `extract.py` | PDF → טקסט, וזיהוי סריקות שאין להן שכבת טקסט |
| `classify.py` | מיפוי ניסוח עברי (״הח׳ דיסקיות״) למערכת בלאי |
| `parsers/eldan.py` | דו״ח ״תעודת זהות לרכב״ של אלדן |
| `parsers/dealer_history.py` | תדפיס ״הסטורית רכב״ של היבואן |
| `parsers/fuel_receipt.py` | קבלת דלק (פז ודומיהן) עם שכבת טקסט |
| `ocr.py` | קריאת מסמכים סרוקים במודל ראייה, עם אימות אריתמטי |
| `load.py` | איחוד כל המקורות והסרת כפילויות |
| `analyze.py` | מרווחים, קצב נסיעה, תחזית, בלאי, עלויות, התראות |
| `fuel.py` | צריכת דלק ועלות — נמדדת מתדלוקים, או אומדן לפי קילומטראז׳ |
| `build.py` | CLI שכותב את `public/vehicle-data.json` |

## דלק

עלות הדלק מחושבת באחד משני מצבים, והפלט תמיד מציין באיזה:

- **נמדד** — כשיש מכל שאפשר לסגור עליו חלון: שני תדלוקי מכל-מלא עם מד אוץ,
  או תדלוק בודד עם `km_since_last_fill` ממחשב הדרך.

קבלות דלק לא מדפיסות מד אוץ, ולכן תדלוק שנקרא מקבלה נכנס להוצאה אבל לא לצריכה
עד שמוסיפים לו את הקילומטראז׳ ידנית. מכל שהצריכה המשתמעת ממנו חורגת מטווח סביר
נפסל עם אזהרה — זה הסימן שחסר תדלוק ברצף, שמפר את הנחת ה-tank-to-tank.
- **אומדן** — כשאין תדלוקים. ההוצאה נגזרת מקצב הנסיעה, מהצריכה שב-`data/config.json`
  ומהמחיר לליטר.

אומדן הוא לא מדידה, ומספר שמחליק בשקט בין השניים גרוע ממספר שלא קיים. לכן
המצב מסומן בבירור גם ב-JSON וגם בדשבורד.

מחיר הדלק נשמר כהיסטוריה ב-`config.json` (`price_history`), כך שכל תאריך מתומחר
לפי המחיר שהיה בתוקף אז. כשהמחיר משתנה — מוסיפים שורה בראש הרשימה.

**קריאות מד אוץ מתדלוקים מזינות גם את ניתוח הטיפולים.** טיפולים מרוחקים זה מזה
שנה, וקצב נסיעה שנגזר מהם בלבד מתיישן ביניהם. קבלת דלק נושאת מד אוץ עדכני בהרבה,
והיא מעגנת את ההערכה טוב יותר מאשר אקסטרפולציה של שנה מהביקור האחרון במוסך.

## הערות על הנתונים

**מסמכים חופפים ממוזגים.** אותו ביקור מופיע גם אצל חברת הליסינג וגם אצל היבואן,
עם פרטים שונים בכל אחד. שני רישומים מאותו ביקור מזוהים לפי קרבה בתאריך
(עד 7 ימים) ובמד האוץ (עד 200 ק״מ), וממוזגים לרשומה אחת. כך, למשל, הטיפול
מ-06/03/2023 מקבל את תווית התוכנית (120,000) מדו״ח אלדן ואת החלפת רצועת התזמון
מתדפיס היבואן — פרט שמופיע רק שם.

**קצב הנסיעה נמדד על חלון זמן, לא על מספר קבוע של טיפולים.** הרכב עשה
כ-20,000 ק״מ בשנה בתקופת הליסינג וכ-8,400 ק״מ בשנה מאז, וממוצע על פני
המעבר הזה נותן קצב שהרכב מעולם לא נסע בו. לכן החישוב מסתמך רק על המרווחים
שנסגרו בשנתיים האחרונות.

**עלות לק״מ לא כוללת את החשבונית הראשונה.** היא מגדירה את תחילת התקופה
הנמדדת, וההוצאה שלה שייכת לתקופה שלפניה.

**התחזית משתמשת במרווח שהבעלים בפועל נוהג בו** כשהוא צפוף יותר מתוכנית היצרן —
זה מה שיקרה בפועל בטיפול הבא.

**כשמד האוץ ומחשב הדרך לא מסכימים, מחשב הדרך מנצח.** הפרש מד האוץ מודד את
המרחק מאז התדלוק *הרשום* האחרון; מחשב הדרך מודד מאז התדלוק *בפועל*, כי הוא
מתאפס בכל תדלוק בין אם נרשם ובין אם לא. לכן פער גדול ביניהם פירושו שיש
תדלוקים חסרים ברישום, ומחשב הדרך הוא זה שמתאר את המכל הנוכחי. כשהם מסכימים
(עד 15%) נלקח מד האוץ, המדויק יותר.

זה תופס מקרה שבדיקת הטווח לבדה מפספסת: הפרש מד אוץ שמשתרע על תדלוקים חסרים
יכול לייצר מספר שנראה סביר — 4.06 ל׳/100 ק"מ — ולחצות את הצריכה המדודה בשקט.

**תדלוק חלקי לא סוגר חלון מדידת צריכה.** אם לא מילאת מכל מלא, לא ידוע כמה דלק
היה בו, ולכן הליטרים של התדלוק הבא לא מתארים את כל המרחק. התדלוק עדיין נספר
בהוצאה — רק לא במדידת הצריכה.
